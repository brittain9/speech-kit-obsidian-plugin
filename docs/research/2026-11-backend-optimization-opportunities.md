# Backend optimization opportunities for Speech Kit

Source review, 2026-11-17. These are proposed experiments based on Speech Kit source at `296146e3`, upstream documentation and the project's recorded evaluations. This review did not run comparative inference benchmarks. Performance and coverage gains are hypotheses until measured through the product path.

## Recommended order

| Priority | Experiment | What it could improve | Compare first |
| --- | --- | --- | --- |
| 1 | Tune ONNX Runtime CPU sessions and profile the stages around them | Live dictation latency, battery use, low-core devices | Moonshine Tiny and Nemotron multilingual 560 ms, default CPU vs. bounded threads and spinning disabled |
| 2 | Prototype Vulkan in the existing GGML runtimes | GPU acceleration for AMD and Intel systems on Windows and Linux | One Whisper checkpoint first, then HY-MT 2 and Qwen if the benefit justifies it |
| 3 | Optimize context allocation and measured CPU work in the llama.cpp helpers | Faster short requests and lower peak RAM/VRAM | Qwen 0.6B and HY-MT 2 1.8B with current weights and outputs held constant |
| 4 | Compare the NVIDIA native Nemotron runtime with the installed ONNX configuration | Faster multilingual live ASR where the encoder dominates | Same checkpoint and chunk profile when provenance permits, first on Apple silicon or NVIDIA CUDA |
| 5 | Trial one NPU path for one graph | Lower energy or better latency on a defined device | Whisper Core ML encoder vs. shipping Metal on Apple silicon |
| Parallel | Benchmark a small number of targeted accuracy improvements | Cleaner long files, proper nouns and constrained multilingual dictation | Tuned segmentation and endpointing, plus a compact English batch candidate |
| Separate product work | Prove a narrow foreground mobile path | Local transcription inside Obsidian on phones and tablets | One compact model in each actual Obsidian WebView |

The checkout packages CPU builds for Apple silicon, Windows x64/ARM64 and glibc Linux x64/ARM64, with Metal on Apple silicon and a separate CUDA variant on x64 Windows and Linux. Whisper, Qwen3 ASR and HY-MT 2 can use those GPU paths. Moonshine, Nemotron, Parakeet Unified, Cohere Transcribe, Pocket TTS and Supertonic use ONNX on CPU. Bergamot runs on CPU in an isolated WebAssembly worker. Linux and Windows ARM64 builds target ARMv8.2+. Mobile and Intel Mac have no package. Check installed-build capabilities separately. [Hardware support](../guides/model-hardware-support.md), [release targets](../../.github/workflows/release.yml), [ARM build flags](../../.github/actions/setup-sidecar-rust/action.yml).

## 1. Make the existing CPU path cheaper

- **Sweep thread count and spinning per workload.** The shared ASR builder uses ORT session defaults. ORT normally creates an intra-op pool per session sized to physical cores and enables thread spinning. A streaming ASR family can load separate encoder, predictor and joiner sessions alongside VAD. Try 1/2/4 threads and the current default, with spinning enabled and disabled. Compare small pools for VAD/predictor/joiner and a larger encoder pool. Test a shared pool only if profiles show contention between sessions. Sessions for Pocket TTS and Supertonic already set two intra-op threads and one inter-op thread, so hold those settings for the first comparison. The pinned Rust bindings expose these controls. [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html), [ORT Rust session options](https://docs.rs/ort/2.0.0-rc.12/ort/session/builder/struct.SessionBuilder.html), [ASR session builder](../../native/src/runtimes/onnx.rs), [Nemotron adapter](../../native/src/adapters/nemotron_asr.rs), [Pocket TTS](../../native/src/adapters/pocket_tts.rs), [Supertonic](../../native/src/adapters/supertonic.rs).
- **Profile copies and repeated work around inference.** Time feature generation, each ONNX session, and token decoding separately. Pocket TTS clones recurrent state arrays when building graph inputs, so measure heap and copy cost before trying reusable buffers or borrowed CPU tensors. For the Nemotron predictor and joiner, measure call counts and copy volume against encoder time. Only test I/O binding or device-resident caches in a graph path proven to run on a device. On a fragmented accelerator path, host/device transfers can dominate short chunks. [Pocket TTS state tensors](../../native/src/adapters/pocket_tts.rs), [Nemotron chunk execution](../../native/src/adapters/nemotron_asr.rs), [ORT profiling](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html), [ORT I/O binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html).
- **Separate cold-start work from inference.** Profile session creation and model lifetime first. If graph optimization is a material cold-start cost, test a locally generated optimized graph keyed by model hash, ORT version, provider/options and compatible hardware, with normal load as the recovery path. ORT documents that offline layout optimizations can depend on the target CPU features. Existing warm retention for read aloud and translation already trades memory for lower next-request latency. Measure cold, warm, idle and resume costs before moving a retention boundary. [ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html#onlineoffline-mode), [Speech Kit power research](2026-11-power-saving-options.md).
- **Treat model precision as an artifact experiment.** Nemotron and Parakeet Unified already use INT8 exports, and Cohere already has FP16, INT8 and Q4 entries. For an unquantized graph with proven expensive operators, compare the original against a reproducible CPU-friendly quantization with quality checks. ORT's CPU documentation favors S8S8 QDQ as the starting point and calls out cases where quantization can hurt speed or accuracy. A smaller file can improve storage and load time while leaving runtime speed unchanged. [Speech Kit catalog](../../native/catalog.json), [ORT quantization](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html).

## 2. Add GPU coverage through the existing runtimes

**Vulkan is the best first reach experiment.** Both pinned Rust wrappers expose a Vulkan build feature. Keep it an optional test variant at first. Start on one AMD GPU and one Intel integrated GPU, then verify Windows and Linux packaging, drivers, device selection and CPU recovery. Use shipping CPU on each machine and CUDA on an NVIDIA comparison machine. Run real product requests with identical model artifacts. Treat Qwen's multimodal encoder and decoder as separate offload checks. A Vulkan-capable build does not establish that a given checkpoint, quantization or operator runs well on that device. [Whisper Rust features](https://docs.rs/crate/whisper-rs/0.16.0/features), [llama.cpp Rust features](https://docs.rs/crate/llama-cpp-2/0.1.160/features), [llama.cpp builds and device selection](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md), [whisper.cpp Vulkan path](https://github.com/ggml-org/whisper.cpp#vulkan-support).

This is more than adding Cargo features. Current Speech Kit acceleration selection recognizes CPU, CUDA and Metal when loading GGML models, and the helpers compile-gate GPU loading to Metal/CUDA. Implementations would need runtime capability reporting and a verified device, separate requested and effective identities, explicit CPU behavior, documented packaging/driver dependencies, and recovery for missing libraries and insufficient memory. Try ROCm or Intel-specific tooling only if Vulkan fails a meaningful target test. Existing CPU support remains the baseline for older drivers and devices. [Cargo features](../../native/Cargo.toml), [capabilities](../../native/src/engine/capabilities.rs), [Whisper runtime](../../native/src/runtimes/whisper_cpp.rs), [Qwen helper model](../../native/src/qwen_asr_model.rs), [HY-MT helper](../../native/src/bin/translation_helper.rs), [llama.cpp backend builds](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md).

## 3. Improve the llama.cpp helpers with current artifacts

Qwen has an eight-thread policy, fixed 4,096-token context and 512-token batch/microbatch. It creates a fresh context per utterance to clear KV state, while holding the model and audio encoder loaded. HY-MT creates a fresh 8,192-token context per translation unit with an 8,192-token batch buffer and up to 4,096 generated tokens. Both request broad layer offload or use CPU. Measure load, context creation, audio encode or prompt prefill, and token generation separately on the 0.6B/1.8B starting models. [Qwen helper model](../../native/src/qwen_asr_model.rs), [HY-MT helper](../../native/src/bin/translation_helper.rs).

- Sweep threads and batch/microbatch sizes on representative audio lengths and text sizes. Size the working context from the validated input length plus generation budget where this preserves context bounds, termination and output. Explore safe reuse with explicit KV reset only if context allocation is a measured bottleneck. Cover cancellation and consecutive unrelated inputs to catch stale context or carryover.
- For memory-constrained GPUs, test a measured partial-offload policy against CPU and full offload, and inspect actual layer placement. Use it only where the saved memory buys reliable acceleration for machines that cannot fit all layers.
- If memory is still limiting, compare a lower quantization of the same weights or smaller KV cache precision. Check model accuracy independently of backend speed, especially names and mixed-language audio for Qwen, and terminology/numbers/format preservation for HY-MT. Use upstream microbenchmarks for prompt versus generation behavior and Speech Kit helper evaluations for real end-to-end latency and output. [llama.cpp benchmark](https://github.com/ggml-org/llama.cpp/tree/master/tools/llama-bench), [llama.cpp quantization](https://github.com/ggml-org/llama.cpp/tree/master/tools/quantize), [Qwen evaluations](../quality/2026-11-17-qwen17-observations.json), [translation benchmark notes](../quality/translation-model-comparison.md).

## 4. Compare native Nemotron and test one ONNX graph at a time

The code explicitly records that a generic CUDA ONNX provider performed poorly or unsafely on tested ASR exports. ORT assigns graph partitions to providers according to operator support. A successful session load can still entail CPU-heavy execution, repeated transfers, or unsupported inputs at runtime. Try one known expensive graph with representative inputs and inspect provider placement and transfers. For streaming RNNT, a reasonable first test is an encoder on the accelerator, with the frequent predictor and joiner calls on CPU. Include initial silence, short final chunks, resets and repeated utterances. This is an experiment about benefit from a specific checkpoint, graph and hardware combination. [Current ASR session policy](../../native/src/runtimes/onnx.rs), [prior CUDA investigation](https://github.com/brittain9/speech-kit-obsidian-plugin/pull/327), [ORT provider partitioning](https://onnxruntime.ai/docs/execution-providers/), [ORT I/O binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html).

| Candidate | Best first use | Decision factor |
| --- | --- | --- |

Compare matching checkpoint and chunk semantics where possible. Attribute any differences to the whole stack when the GGUF and ONNX artifacts or chunk profiles differ. Integration would need an adapter, packaging, managed artifacts and validation at VAD boundaries. Preserve the existing isolation between independently built GGML runtimes. ### What existing Speech Kit results support

- On an Apple M2 Pro CPU run, Whisper Small Multilingual took 0.70 s of compute for one short German clip versus 3.60 s for Turbo. Whole-process peak RSS was 716 MB versus 1,561 MB. Turbo was more accurate on both natural German readings and several other language fixtures. This supports testing a resource-saving choice for specific workloads. [Matched local observations](../quality/2026-11-16-compact-multilingual-whisper.md#matched-local-observations)
- On the same Mac model, the Qwen 0.6B helper processed two short clips in 812/859 ms on the CPU run and 349/520 ms with Metal device access. The larger 1.7B used 786/812 ms with Metal and the wording was effectively the same across sizes on these clips. The run used one helper load per size and route, different diagnostic builds for CPU and Metal, and one observation per clip. These figures identify a backend worth measuring and provide little evidence of an accuracy gain from 1.7B. [Retained Qwen observations](../quality/2026-11-17-qwen17-observations.json)
- The 560 ms buffered Parakeet profile accumulated 106.4 s of inference on 66.75 s of speech in one project stress run. The 1,120 ms profile accumulated 19.5 s on the same audio and completed without a queue error. Screen sustained backlog before treating shorter chunking as a speed improvement. A separate Parakeet TDT batch export failed natural German in two decoders, so a runtime comparison should start with streaming Nemotron and leave TDT outside the initial scope. [Streaming comparison](2026-11-nvidia-asr-options.md#validation-scope), [TDT evidence](../quality/2026-11-16-compact-multilingual-whisper.md#architecture-and-model-research-outcome)

## Reaching mobile and smaller desktop devices

For broader desktop reach, measure the small CPU models on an actual low-power ARM64 or x64 device, and profile model startup, peak memory and sustained real time under thermal and concurrent load. Expanding to older ARM machines needs separate review of the instruction-set requirements of the sidecar and its native libraries. Include old CPUs in the build/run acceptance matrix before advertising compatibility. [Packaged platforms](../guides/model-hardware-support.md), [ARM build configuration](../../.github/actions/setup-sidecar-rust/action.yml).

Obsidian on iOS and Android does not expose Node or Electron APIs. The desktop plugin imports Node and launches a native executable with child_process, and the manifest declares the plugin desktop-only. A native ORT or Sherpa mobile build alone therefore cannot make Speech Kit work in mobile Obsidian. [Obsidian mobile development](https://docs.obsidian.md/Plugins/Getting%20started/Mobile%20development), [manifest](../../manifest.json), [sidecar launcher](../../src/sidecar/sidecar-process.ts).

For mobile Obsidian, start with foreground short-clip transcription using one compact ASR model in a WebAssembly worker. Verify microphone permissions, worker and asset loading, offline storage, actual device memory, and note insertion in both WebViews. Assume one WASM thread until cross-origin isolation and thread support are observed. Add WebGPU only if the actual WebViews expose it and the model benefits. If native acceleration, system-level dictation or background capture is the priority, a native companion is a separate product path. ORT and Sherpa offer mobile libraries for a companion, with CPU/XNNPACK and device-specific providers subject to their own compatibility and operator limits. [ORT Web thread and worker options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html#envwasmnumthreads), [ORT WebGPU](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html), [ORT mobile](https://onnxruntime.ai/docs/tutorials/mobile/), [Sherpa platform matrix](https://github.com/k2-fsa/sherpa-onnx#supported-platforms).

## First two experiments and how to measure them

1. **Existing models, tuned CPU path.** Start with Moonshine Tiny and multilingual Nemotron 560 ms. Use unchanged, pinned weights and compare current defaults with two/four threads and with spinning disabled. Change one variable at a time before combining winners. Capture first-partial wall time, speech-end to final wall time, sustained backlog, peak process memory, idle wakeups and active CPU time. Run on the Mac and on an authorized Windows or Linux machine with fewer resources. Check with concurrent read-aloud or translation once the isolated tests look good. A CPU profile earns a default when its gain survives the real app path and preserves transcript and session behavior.
2. **One new desktop GPU path.** Run the same Whisper model and decoding settings on CPU and Vulkan on an AMD or Intel machine. Include a short phrase and a long file to expose startup and data transfer costs. Verify actual offload, compare WER/CER and timestamp continuity, then measure acceleration failure and fallback with an unavailable device. Measure a second vendor before advertising broad support. Take HY-MT next only if the Whisper result justifies packaging work. If the priority is accuracy over device coverage, run the existing-model multilingual file comparison in its place.

Reuse the repository's paced fixtures, real-model tests and environment collector. The current report sums engine duration for real-time factor and measures partial positions on the audio clock. Add wall-clock timing through the user-facing path. Record exact sidecar build, binary/model hashes, execution settings, actual device placement or offloaded layers, power mode, and cold/warm definitions. Alternate repeated A/B runs and report p50/p95 for each workload. For latency changes hold the checkpoint and chunking constant. For model comparisons report every artifact and parameter that changes. [Reproducible evaluations](../quality/reproducible-transcription-evaluations.md), [environment capture](../quality/evaluation-hardware.md), [native test/benchmark entry points](../../native/tests/README.md).

| Workload | Record |
| --- | --- |
| Dictation | Time from speech start to first stable partial, end of speech to committed text, missed ends, repeated/revised words, audio backlog, WER/CER and named-term recall |
| File transcription and meetings | Wall time divided by audio duration, cold model load separately, peak memory, speaker/timestamp retention where applicable, WER/CER and silence false positives |
| Read aloud | Time to first audible PCM at the app boundary, playback underruns, real-time factor, seed/voice, and a fixed prompt set for pronunciation and naturalness |
| Translation | Cold/warm completion times on short and long notes, peak memory, numbers/names/terminology and required formatting, plus the existing translation quality scores for each tested direction |
| Battery/device coverage | Process CPU time and wakeups, sustained package energy where measured, model/package sizes, RAM/VRAM peaks, device driver failures, and successful return to CPU |

A reasonable first decision bar is a repeatable reduction in p95 latency or measured energy on the intended device class without material output degradation, increased capture backlog or unreliable fallback. Agree on numerical thresholds for a particular product change after collecting baseline variability.
